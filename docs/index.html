Platform

Everything a delivery operation runs on

One system of record for orders, drivers, pricing and analytics — every state change event-logged, every rule unit-tested, every endpoint documented.

📦

Order management

Create orders and track the full lifecycle — pending → assigned → in transit → delivered — with an immutable event history per order.

📍

Driver dispatch

Geolocation-aware nearest-driver matching with vehicle filters and live availability heartbeats. Drivers free up automatically on delivery.

💸

Dynamic pricing

Distance-based fees with demand-surge tiers and a minimum-fee floor. When the client omits a demand ratio, the engine derives it live from zone-hour demand forecasts. Every quote returns a full, auditable breakdown.

⏱️

ETA estimation

ETAs served by the registry-promoted LightGBM model (beats the heuristic 5.1 vs 17.8 min MAE on realized deliveries — a 12 km order now quotes 22 min instead of 54). If the model store is down, the transparent heuristic answers instead.

📊

Operational analytics

KPI summaries — status mix, revenue, average delivery time, fleet availability — plus a Prometheus metrics endpoint for alerting.

🤖

AI copilot

Ask "how did we do today?" in plain language — a LangGraph agent queries the governed API with your tenant's credentials, searches the runbook when it's a how question, and narrates incidents when alerts fire.

🛡️

Production discipline

Fully typed (mypy), an 85% coverage floor enforced in CI on three Python versions, dependency CVE audits, Docker packaging, and a protected main branch with required checks.

Why bother

The old way vs the platform way

Same delivery business, two operating models. Every "platform way" claim links to the code that makes it true — no vibes.

📞 The old way — phone calls and spreadsheets

✗Dispatch: "who's free?" — call drivers one by one, hope someone answers.
✗Pricing: a flat fee someone picked in 2019, same at noon and at midnight.
✗Records: "it probably delivered" — no trail, so disputes end in refunds.
✗Forecasting: none — yesterday's queue size is the plan.

⚡ The platform way — this repository

✓Dispatch: the nearest-available-driver algorithm picks with a vehicle filter, in milliseconds.
✓Pricing: auditable tiers — base + per-km, surge from the live demand ratio, hard-capped.
✓Records: an immutable event log — every transition on Kafka, replayable, quality-gated in the warehouse.
✓Forecasting: zone-hour demand forecasts feed the surge tiers, refreshed hourly by Airflow.

AI layer

The copilot that reads your data — and explains your incidents

One agent over the governed API, wrapped in the reliability layers an LLM needs in production: guardrails, budgets, a measured fallback chain, full tracing, and an eval set that fails the build on regression.

🧠

The agent

A LangGraph supervisor whose read-only tools execute on the request's own session — Postgres RLS scopes every answer to the caller's tenant. pgvector RAG serves the how questions from the runbook, the decision records — and your own Obsidian notes.

🛟

The safety net

Injection screening and question caps answer 422 before any model call; tool-call and token budgets end the loop gracefully; the fallback chain (flagship → mini → canned) reports which rung served and why — degraded_reason in the payload, not the logs.

📈

The evidence

One MLflow run per conversation (provider, rung, cost, full message log); a versioned golden eval set runs in CI — wrong tool, broken shape, budget that stops stopping all fail the build — and a scheduled Airflow eval scores the live provider daily.

🚨

The narrator

When a pipeline task fails, the alert arrives already explaining itself: what broke, the current outbox backlog and relay age, the benchmark run it correlates with, the first checks. Fails open per source — the alert never waits for prose.

FAQ

The questions an interviewer actually asks

Is this production-ready?

Direct answer: the core platform, the data plane and the ML loop are; the honest distance to a real-life system is published in docs/roadmap.md — JWT auth, versioned migrations, and per-tenant isolation enforced by Postgres Row-Level Security are live; load testing and deeper data are the named next steps. Every claim links to code or a benchmark.

How accurate is the ETA?

Benchmarked, not claimed: the LightGBM model beats the heuristic champion on a time holdout (MAE 5.1 vs 17.8 minutes overall; 5.1 vs 22.1 on >10 km trips — reports in data/benchmarks). Promotion to the serving registry only happens if a challenger beats the champion, and the heuristic stays as the fallback so quoting never breaks.

Why is surge capped at 2.0×?

Modern platforms run in a 1.2×–2.5× band; capping at 2.0× with the demand ratio floored at 0.5 and capped at 2.5 keeps surge explainable to customers and auditable in pricing_rules.py. The ratio itself derives from observed vs forecast demand per zone-hour — not from a manager's hunch.

How do you handle time zones and DST?

Storage is UTC everywhere; local business grains derive through the IANA tz database (BUSINESS_TIMEZONE) — never a fixed offset. The backfill window deliberately crosses the October DST transition, so the marts prove it: the same 7 pm local hour is 17:00 UTC in summer and 18:00 UTC in winter.

Is it multi-tenant?

Yes — isolated by the database engine, not by remembering WHERE clauses. The JWT carries the issuing user's tenant binding; every request pins it into Postgres row-level-security policies (forced on all six business tables, migration 003), so a second tenant's reads and writes physically cannot touch the first tenant's rows — demonstrated live with a second tenant onboarded through POST /tenants. Each tenant can also run its own fee/surge configuration (PUT /pricing/config), and the warehouse's raw layer keeps the tenant inside the event envelope. The trade-offs and graduation path (schema-per-tenant, database-per-tenant) are written up in docs/decisions/0001-multi-tenancy.md.

What happens when the ML model is wrong or down?

Three guards: the champion heuristic always stays as the fallback (a down registry costs a gauge point, not outages); promotion is champion-gated so a bad challenger never serves; and every forecast hour is predicted, never observed — the current hour can't be priced on partial data.
